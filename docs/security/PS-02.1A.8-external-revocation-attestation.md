# PS-02.1A.8 — External credential revocation attestation

## Security contract

A credential-store adapter must not report successful revocation with a boolean.
Its `revoke_session(session_id)` operation returns a provider-signed
`CredentialRevocationReceipt` containing:

- exact immutable session UUID;
- HTTPS issuer identifier;
- customer-pinned signing key identifier;
- timezone-aware revocation timestamp;
- outcome exactly `revoked`;
- Ed25519 signature over the canonical version-1 JSON payload.

The canonical payload uses sorted keys and compact JSON, with the fields
`issuer`, `key_id`, `outcome`, `revoked_at`, `session_id`, and `version`.
The signature is base64-encoded Ed25519 output. Receipt signatures are
verified against a customer-provisioned public key indexed by issuer and key
identifier. No key discovery from the receipt or an untrusted network endpoint
is permitted.

## Runtime behavior

The coordinator marks `credential_revoked` true only after signature
verification succeeds and the receipt session UUID exactly matches the
requested session. Missing, malformed, unsigned, unknown-key, wrong-session,
or tampered receipts are treated as unconfirmed credential revocation.
Database admission fencing and exact-backend termination are still attempted
independently. The coordinator never reports complete revocation without both
the signed external receipt and verified PostgreSQL containment.

The append-only PostgreSQL audit record stores the canonical receipt payload
and signature as evidence. The database checks that the receipt is bound to
the same session UUID and requires receipt evidence for a `verified` event.
An independent auditor can re-verify the Ed25519 signature offline using the
customer's separately controlled trust anchor. PostgreSQL does not claim to
cryptographically verify the external vault signature itself.

## Customer deployment requirements

1. Select and operate a customer-controlled credential store that can issue
   signed revocation receipts. This provider-neutral code does not claim an
   integration with any specific vault.
2. Generate and protect the Ed25519 private signing key in customer-controlled
   key management. The application must not possess that private key.
3. Deliver the raw 32-byte public key and exact issuer/key identifier through
   an authenticated deployment configuration channel.
4. Implement the credential-store adapter so successful exact-session
   revocation returns the signed receipt. A store outage must not fabricate a
   receipt.
5. Apply the revised migration 0016 in a customer test database and verify
   receipt persistence, append-only behavior, and offline signature checking.
6. Retain key-rotation and historical public-key material for the audit
   retention period.

## Explicit limitations

- No production vault adapter or customer signing key is included.
- No customer database migration has been applied by this change.
- A receipt is an external system's signed assertion; its assurance depends on
  the customer's vault controls, signing-key protection, and adapter behavior.
- This code does not establish production certification.
