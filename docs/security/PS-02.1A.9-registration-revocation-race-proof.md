# PS-02.1A.9 — Registration/revocation race proof

The PostgreSQL integration suite now exercises both lock orderings on the same
session-binding row.

## Registration obtains the shared lock first

The PS-02.1A.5 harness opens two dedicated session logins. Each transaction
registers its own physical backend, then deliberately holds the transaction
open while sleeping. The revocation operation is started only after both
registration transactions are observed inside that lock-holding interval.

Expected result:

1. Both registrations commit while holding the shared admission lock.
2. Revocation waits for those transactions to release the row lock.
3. Revocation marks the session inactive and prevents new logins.
4. Exact PID plus backend-start termination kills the two still-live sessions.
5. The termination result reports exactly two terminated backends and zero
   remaining registered backends.

## Revocation obtains the update lock first

The PS-02.1A.9 harness establishes a real session-login connection before
revocation starts, then holds that connection at a pre-registration barrier.
The revocation transaction updates the session binding and deliberately keeps
its transaction open. Only after the revocation transaction is observed
holding the fence does the already-authenticated session attempt registration.

Expected result:

1. The registration request blocks on the shared row lock.
2. Revocation commits the inactive fence and NOLOGIN state.
3. The waiting registration resumes and fails because the session is no longer
   active.
4. No backend registry row or `backend_registered` audit event is written.

The two tests are executed against PostgreSQL 14, 15, 16 and 17. They use
separate physical database connections and actual per-session login roles,
not mocks or a shared administrator connection.
